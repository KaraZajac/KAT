# X10 Protocol

**Rust module:** `src/protocols/x10.rs`
**Reference:** `REFERENCES/Flipper-ARF/applications/system/subghz_garage/protocols/x10.c` (@CodeAllNight's decoder).
Flipper-ARF's garage app registers it in RX group g1 and ships a TX plugin (`tx_x10`), so it is the reference that
decodes and transmits X10. Momentum, RogueMaster and FoxFW (`lib/subghz/protocols/x10.c`) register the same decoder
without an encoder; FoxFW's SubRATT random-key app vendors the garage file unchanged except `type` Static instead of
Dynamic (it transmits random codes with the complements filled in); doctor-firmware does not have X10. No Flipper
unit test has an X10 capture.

## Overview

X10 RF home-automation remotes (lamp and appliance modules): a 32-bit code of a house code (A..P), a unit (1..16) and
a command (On, Off, Dim, Bright), each command byte followed by its complement. The complements are the check.

## Timing / modulation

| Parameter | Value | Notes |
|-----------|-------|-------|
| Preamble HIGH | 9600 µs (16·te_short) | window ± 700 µs |
| Preamble LOW | 4800 µs (8·te_short) | window ± 500 µs |
| Bit HIGH | 600 µs (te_short) | ± 100 µs |
| Bit 0 LOW | 600 µs | ± 100 µs |
| Bit 1 LOW | 1800 µs (te_long) | ± 200 µs |
| Closing HIGH | 600 µs | ± 100 µs; it ends the frame |
| Gap | 43200 µs (72·te_short) | encoder only |
| Bits | 32 | MSB first |

AM (OOK); the C flags 315 MHz ("technically it is 310MHz only"). All windows are strict (`DURATION_DIFF < delta`).

## Frame Layout

From the C's comment (CM17A protocol): `SSSSXBXX ssssxbxx DBOQBXXX dboqbxxx`, the lower-case bytes being the
complements of the upper-case ones.

| Bits | Field |
|------|-------|
| 31..28 | house code (the C's `serial`; letter = "MNOPCDABEFGHKLIJ"[serial]) |
| 26 | unit bit 8 (units 9..16) |
| 23..16 | complement of bits 31..24 |
| 15 | dimmer |
| 14, 11 | unit bits 4 and 2 |
| 13 | Off |
| 12 | unit bit 1 |
| 7..0 | complement of bits 15..8 |

`subghz_protocol_x10_check_remote_controller`: serial = bits 31..28, btn = bits 26..24 | bits 15..11 << 3. The C
displays the unit as 1 + (btn 0x10 → 1, 0x08 → 2, 0x40 → 4, 0x04 → 8), Off when btn & 0x20, and the dimmer codes
btn 0x98 = Dim, 0x88 = Bright.

## Decoder Steps

1. Reset: a HIGH with |d − 9600| < 700.
2. The next pulse must be a LOW with |d − 4800| < 500, else reset.
3. HIGH/LOW pairs: HIGH ≈ 600, LOW ≈ 600 → 0, ≈ 1800 → 1; anything else resets.
4. After 32 bits the closing HIGH (≈ 600) ends the frame: it is reported when byte 2 = !byte 1 and byte 4 = !byte 3
   (`subghz_protocol_x10_validate`). The C's reset is complete (data, count, step), so every copy of a press decodes.

## Field mapping

`serial` = house code index, `button` = the C's btn (labels as the C prints them: "Button 3 On", "Button 9 Off",
"Dim", "Bright"); `counter` None; `data` = the 32 bits; `crc_valid` = both complements hold (always for decodes);
`encoder_capable` true.

## Encoder

`subghz_protocol_encoder_x10_get_upload` (`encoder.repeat` = 3): HIGH 9600, LOW 4800, the 32 bits (HIGH 600 + LOW
600 / 1800), HIGH 600, LOW 43200; 3 copies. The captured code is sent: no copy of the C changes the button, so
"Send button…" lists nothing.

## Key file

`Protocol: X10`, `Bit: 32`, `Key`; loading requires `Bit: 32` (a key whose complements fail still loads, as in the C).

## Validation

Reference oracle: `REFERENCES/tools/oracle/bin/subghz_oracle_garage` (the garage app's C, decoder + TX-plugin
encoder); parity tools `F_FILES` / `F_KEYS` in `src/protocols/f_common.rs`.

- No Flipper unit test has an X10 capture. On the 304 RAW captures of IMPORTS and the three unit-test folders, the
  C decoder and KAT's both report nothing.
- Encoder: 70 random key files (every house code, Dim / Bright, 10 with broken complements, 4 with bits above 32)
  — pulse-identical to the garage oracle's `encode`.
- Decoder: 800 fuzz RAW files (200 per protocol of its group: jitter, dropped / split / stretched pulses, window-edge
  values, scaled timing, wrong bit counts, mixed codes, broken complements) decoded by the X10 decoder alone (reset
  after each report, as `decode --protocol X10`): identical, 287 frames.
- Registry: X10 transmissions decode as X10 only; `kat_diff.py` over IMPORTS and the unit tests shows no change.
- Unit tests: every copy decodes, upload layout, the C's fields and labels, preamble and bit window bounds, broken
  complements and wrong lengths rejected, key-file round trip.
